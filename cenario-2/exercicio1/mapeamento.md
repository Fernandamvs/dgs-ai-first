# Mapeamento de MCP Servers — NovaTech Assistant

Objetivo: cobrir as 5 necessidades de acesso do projeto com o menor escopo possível por server, evitando que um único server "vazado" ou mal configurado dê acesso a mais do que o estritamente necessário. `infra/` (parâmetros Bicep sensíveis) fica **fora de qualquer server** — nenhuma das 5 necessidades pede acesso a ele, então não há instância de filesystem apontando para lá.

## Princípio de configuração

O `@modelcontextprotocol/server-filesystem` não tem, por padrão, um modo "somente leitura" nativo por diretório — todas as instâncias expõem o mesmo conjunto de tools (`read_file`, `write_file`, `edit_file`, `move_file`, `create_directory`, `list_directory`, `search_files`, `get_file_info`, `list_allowed_directories`). Por isso, o "somente leitura" das necessidades 2 e 3 é obtido combinando duas coisas:

1. Uma **instância dedicada** do server, com `args` apontando só para a pasta em questão (isolamento por caminho).
2. Uma regra de **permissão do Claude Code** (`settings.json` → `permissions.deny`) bloqueando as tools de escrita daquela instância (`write_file`, `edit_file`, `move_file`, `create_directory`), deixando só as tools de leitura liberadas.

O mesmo padrão vale para o git: o `mcp-server-git` expõe tools de leitura e de escrita no mesmo processo, então o escopo mínimo da necessidade 4 é obtido negando as tools que alteram o repositório.

## Resumo de exclusões deliberadas

- `infra/` (parâmetros sensíveis do Bicep) — **não coberto por nenhum server**; nenhuma das 5 necessidades o requer.
- Nenhuma instância de filesystem usa uma allow-list na raiz do repo (`.`) — cada uma aponta só para a pasta que a necessidade pede, evitando que uma tool de leitura "vaze" para pastas vizinhas.
- O server de git não recebe escopo de escrita em nenhuma necessidade listada; se no futuro for preciso commitar via MCP, isso deve ser uma 6ª necessidade explícita, não uma extensão silenciosa desta.
